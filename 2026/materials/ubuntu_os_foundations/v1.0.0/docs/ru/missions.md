# Основы Ubuntu и ОС — самостоятельные задания

[日本語](../ja/missions.md) · [Русский](../ru/missions.md) · [O‘zbekcha](../uz/missions.md)

> Этот перевод пока не отражает действующие задания M1–M7: прежний M0 теперь является упражнением P0. Для заданий, которые проверяет Lab, используйте актуальную японскую версию в репозитории OS-Linux-Control.

Задания: Mission 0–7.

Среда: Ubuntu Server 24.04 LTS.
Темп: переходите к следующей Mission по мере готовности, а не по номеру занятия.

В M0–M7 команды нужно выбирать самостоятельно. Если нужны полностью расписанные действия, сначала пройдите [пошаговые упражнения P1–P6](practice.md).

P и M используют разные ресурсы. Завершённое P не даёт PASS в соответствующем M. Рекомендуемый порядок: `P1 → M1 → P2 → M2 → … → P6 → M6 → M7`. Для M0 и итогового M7 отдельного P нет.

## Общие действия

При первоначальном создании среды все Mission уже находятся в незавершённом состоянии. Сбрасывать их перед первым выполнением не требуется.

### Под какой учётной записью работать

После подключения к Ubuntu управляющий пользователь — `ssm-user`. Проверьте это:

```bash
id -un
```

`jdu-check` и `jdu-reset` всегда выполняйте от имени `ssm-user`. Если запустить их под другим пользователем, они подскажут, как вернуться к `ssm-user`, и завершатся.

Учётные записи для упражнений: `jduops`, `jduviewer`, `jduwriter`. Пример переключения из `ssm-user`:

```bash
sudo su - jduops
id
```

Вернитесь к `ssm-user`:

```bash
exit
id -un
```

Из перечисленных участников только `ssm-user` может выполнять `sudo` без пароля. Не пытайтесь напрямую переходить из `jduwriter` в `jduviewer`: сначала выполните `exit`, вернитесь к `ssm-user` и затем запустите `sudo su - jduviewer`.

`jduapp`, `jduweb`, `jdufinal`, `jduworker` — учётные записи служб. Их оболочка входа — `nologin`, поэтому интерактивный `su -` для них не применяют. Нужную проверку выполняют из `ssm-user` одной командой `sudo -u USER COMMAND`.

Проверьте текущую Mission:

```bash
jdu-check M1
```

Если настроен сервер прогресса преподавателя, текущий результат отправляется автоматически, даже когда ещё не все пункты имеют PASS.

`RESULT` — оценка задания на Ubuntu, `REPORT` — результат отправки по HTTPS. Ошибка передачи не меняет PASS/FAIL самой Mission. Посмотреть анонимный ID сервера можно так:

```bash
jdu-progress id
```

Чтобы временно проверить только локально, без передачи:

```bash
jdu-check M1 --no-submit
```

Сбрасывайте Mission только тогда, когда действительно нужно начать её заново:

```bash
jdu-reset M1
```

Сразу после сброса все пункты показывают `FAIL`. Это ожидаемо: LabCheck не исправляет состояние за студента.

## M0. Среда и ОС

На действующей системе определите Ubuntu, ядро Linux, PID 1, текущего пользователя и имя хоста. Запишите шесть значений в `~/jdu-lab/m0/observation.env`:

```text
OS_ID=
OS_VERSION_ID=
KERNEL_RELEASE=
PID1_COMM=
USER_NAME=
HOST_NAME=
```

Берите значения из вывода команд в вашей среде. Не угадывайте.

```bash
jdu-check M0
```

## M1. Оболочка, путь, файл и текст

### Цель

Различать абсолютные и относительные пути; создавать каталоги и файлы; копировать файл; выбирать нужные строки из журнала.

### Начальное состояние

Исходные материалы находятся в `~/jdu-lab/m1/inbox`. `case01` не завершён, в `staging` есть лишние файлы `.tmp`.

### Задание

1. Создайте следующее дерево каталогов:

```text
~/jdu-lab/m1/case01/
├── config/
├── logs/
└── notes/
```

2. Скопируйте `inbox/config/app.conf` в `case01/config/app.conf`.
3. Скопируйте `inbox/logs/incident.log` в `case01/logs/incident.log`.
4. Не меняйте содержимое двух скопированных файлов.
5. Уберите все файлы `.tmp` внутри `case01`.
6. Сделайте владельцем объектов внутри `case01` управляющего пользователя Ubuntu `ssm-user`.
7. Сохраните в `notes/errors.txt` только полные строки `incident.log`, содержащие `ERROR`, без номеров строк.
8. Сохраните в `notes/recent.txt` последние пять строк `incident.log`, не меняя их порядок.

### Проверка

Оцениваются шесть пунктов: каталоги, исходные файлы, отсутствие `.tmp`, владелец, `errors.txt` и `recent.txt`.

```bash
jdu-check M1
```

Полезные команды: `pwd`, `ls`, `tree`, `mkdir`, `cp`, `rm`, `find`, `grep`, `tail`, `stat`.

## M2. Пользователь, группа, права и sudo

### Цель

Различать пользователя, основную и дополнительную группы; настроить групповую работу и setgid в общем каталоге.

### Начальное состояние

`jduops`, `jduviewer` и группа `ops` уже существуют. Сначала только `jduviewer` ошибочно входит в дополнительную группу `ops`, а `jduops` в неё не входит. Владелец, группа и режимы `/srv/jdu-share` и `README.txt` пока не соответствуют заданию.

### Задание

1. Добавьте `jduops` в дополнительную группу `ops`.
2. Удалите `jduviewer` из дополнительной группы `ops`.
3. Назначьте владельца и группу `/srv/jdu-share` как `root:ops`.
4. Установите для `/srv/jdu-share` режим `2775` с setgid. Не разрешайте запись всем пользователям.
5. Установите для `/srv/jdu-share/README.txt` владельца и группу `root:ops`, режим `664`.
6. Из `ssm-user` перейдите через `sudo su - jduops`. Создайте файл в общем каталоге и проверьте, что группа нового файла — `ops`.
7. Проверьте, что `jduviewer` может читать `README.txt`.
8. Проверьте, что `jduviewer` не может создавать файл в общем каталоге.

После проверки под `jduops` вернитесь через `exit` к `ssm-user`. Затем выполните `sudo su - jduviewer`, проверьте его права и снова выйдите через `exit`. Перед `jdu-check M2` убедитесь через `id -un`, что вы — `ssm-user`.

### Проверка

Оцениваются шесть пунктов: членство в группах, владелец и группа каталога, режим каталога, образец файла, наследование группы и доступ `jduviewer`.

```bash
jdu-check M2
```

Полезные команды: `id`, `groups`, `getent passwd`, `getent group`, `stat`, `namei`, `chown`, `chmod`, `usermod`, `sudo -u`.

Запрещено: `chmod 777`.

## M3. Процесс и пакет

Начинайте после глав 8 и 9 и обеих частей упражнения P3. В главе 10 запуск служб и автозапуск изучаются подробнее.

### Цель

Соотнести службу с процессом, отправить сигнал конкретному PID, изучить и установить пакет Ubuntu.

### Начальное состояние

`jdu-m3-process1.service`, `jdu-m3-process2.service` и `jdu-m3-process3.service` работают как обычные юниты systemd. `cmatrix` ещё не установлен. Начальное состояние можно посмотреть так:

```bash
systemctl list-units --type=service 'jdu-m3-*'
systemctl status jdu-m3-process1.service jdu-m3-process2.service jdu-m3-process3.service
```

### Задание A: остановить только process2

1. Найдите Main PID службы `jdu-m3-process2.service`.
2. Проверьте процесс с тем же PID через `ps`.
3. Отправьте `TERM` только этому PID.
4. Убедитесь, что `process2` остановлен, а `process1` и `process3` работают.

Не используйте `pkill` с широким шаблоном, `killall` или сигнал `KILL`.

### Задание B: установить cmatrix

1. Изучите сведения о пакете.
2. Установите `cmatrix` через `apt`.
3. Запустите команду; завершите её через `Ctrl+C`.
4. Проверьте версию пакета и выясните, какой пакет предоставляет `/usr/bin/cmatrix`.

### Проверка

Оцениваются два пункта: всё задание A как один пункт и всё задание B как один пункт. Сдавать файл не нужно.

```bash
jdu-check M3
```

Полезные команды: `systemctl status`, `systemctl show`, `ps`, `kill`, `apt show`, `apt install`, `dpkg-query`, `command -v`, `dpkg -S`.

## M4. Служба systemd

### Цель

Связать файл юнита, службу и процесс; отличать `active` от `enabled`.

### Начальное состояние

Подготовленная преподавателем `jdu-status.service` имеет состояния `loaded`, `inactive`, `disabled`. Файл юнита уже завершён.

### Задание

1. Через `systemctl cat jdu-status.service` прочитайте `User`, `WorkingDirectory`, `ExecStart`.
2. Запустите службу, не меняя файл юнита.
3. Включите автозапуск при загрузке.
4. Отдельно проверьте `active` и `enabled`.
5. Узнайте Main PID и сопоставьте его с реальным процессом.
6. Проверьте соответствие пользователя, командной строки и рабочего каталога процесса настройкам юнита.

### Проверка

Оцениваются три пункта: `active`, `enabled`, соответствие неизменённого юнита процессу. Сдавать файл не нужно.

```bash
jdu-check M4
```

Полезные средства: `systemctl cat`, `systemctl start`, `systemctl enable`, `systemctl is-active`, `systemctl is-enabled`, `systemctl show`, `ps`, `/proc/PID/cmdline`, `/proc/PID/cwd`.

## M5. Порт, сокет и журнал

### Цель

Связать службу, процесс, сокет, IP-адрес, порт, HTTP и журнал в одной работающей системе.

### Начальное состояние

Подготовленная `jdu-web.service` имеет состояния `loaded`, `inactive`, `disabled`. Файл юнита и файл содержимого готовы. На TCP-порту 8081 пока нет ожидающего соединения сокета.

### Задание

1. Прочитайте в файле юнита `User`, `ExecStart`, адрес, порт и путь к содержимому.
2. Запустите `jdu-web.service`, не меняя юнит.
3. Проверьте сокет, ожидающий соединения на `127.0.0.1:8081`. Такое состояние называется `LISTEN`.

```bash
sudo ss -lntp | grep ':8081'
```

4. Сравните PID в поле `users:` вывода `ss` с Main PID службы.

```bash
systemctl show --property MainPID --value jdu-web.service
```

5. Убедитесь, что ожидания нет на `0.0.0.0:8081` или `[::]:8081`.
6. Отправьте запрос на `http://127.0.0.1:8081/` и проверьте HTTP-ответ.
7. Проверьте, что пользователь службы `jduweb` может прочитать файл содержимого. `jduweb` не предназначен для входа, поэтому не используйте `su - jduweb`. Реальное право чтения проверьте так (`0` — разрешено, `1` — запрещено):

```bash
sudo -u jduweb -- test -r /srv/jdu-web/index.txt
echo $?
```

Пользователя и группы можно посмотреть через `getent passwd jduweb` и `id jduweb`, права файла и родительских каталогов — через `stat` и `namei -l /srv/jdu-web/index.txt`.

8. Отправьте запрос на `http://127.0.0.1:8081/m5-check`.
9. Найдите `REQUEST path=/m5-check` в журнале текущего запуска службы.
10. Убедитесь, что на TCP-порту 18081 нет ожидающего сокета и HTTP-запрос на него не проходит.

### Проверка

Оцениваются четыре пункта: сокет и PID, HTTP и доступ к файлу, запись о запросе студента, сравнение открытого и закрытого портов. Запрос `/` от LabCheck не заменяет ваш запрос `/m5-check`.

```bash
jdu-check M5
```

Полезные команды: `systemctl cat`, `systemctl start`, `systemctl show`, `sudo ss -lntp`, `curl`, `sudo -u`, `sudo journalctl`.

## M6. SSH и удалённая работа

### Цель

Различать локальную сторону CloudShell и удалённую Ubuntu; использовать удалённую команду SSH, отправку и получение файлов через `scp`.

### Начальное состояние

SSH-ключ, псевдоним `jdu-ubuntu` и туннель Session Manager уже настроены. Они не оцениваются. Файлы Mission на CloudShell и Ubuntu ещё не созданы.

### Задание

1. На CloudShell проверьте `id -un`, `hostname`, `pwd`.
2. Через `ssh jdu-ubuntu` или удалённую команду SSH проверьте те же три значения на Ubuntu.
3. Запишите в CloudShell `~/jdu-lab/m6/local-source.txt` ровно одну строку:

```text
JDU SSH transfer test
```

4. Загрузите файл через `scp` на Ubuntu как `~/jdu-lab/m6/upload.txt`.
5. Через удалённую команду SSH создайте на Ubuntu `~/jdu-lab/m6/remote-result.txt`. Не вводите значения вручную.

```text
REMOTE_USER=<пользователь, определённый на Ubuntu>
REMOTE_HOST=<имя хоста, определённое на Ubuntu>
REMOTE_PATH=<домашний каталог, определённый на Ubuntu>
```

6. Скачайте `remote-result.txt` через `scp` в CloudShell как `~/jdu-lab/m6/downloaded-result.txt`.
7. Сравните через `sha256sum` источник и адресат загрузки, а затем источник и адресат скачивания.

### Проверка

На стороне Ubuntu проверяются два пункта. Выполните команду после входа SSH в Ubuntu. Результат поступит в `M6 Ubuntu` на панели прогресса.

```bash
jdu-check M6
```

На стороне CloudShell проверяются четыре пункта. Выйдите из Ubuntu через `exit`, вернитесь в CloudShell и выполните:

```bash
jdu-check M6
```

Панель показывает для M6 отдельно Ubuntu `2/2`, CloudShell `4/4` и общий итог `6/6`. Mission завершена только при PASS всех пунктов с обеих сторон. Повторная проверка одной стороны сохраняет последний результат другой.

Добейтесь полного PASS на обеих сторонах. Не выводите, не сдавайте и не переносите закрытый ключ. Не меняйте SSH-службу, настройки SSH и `authorized_keys`.

Полезные команды: `ssh`, `scp`, `sha256sum`, `id`, `hostname`, `pwd`, `printf`.

## M7. Итоговая проверка Ubuntu

### Цель

Самостоятельно применить знания M2, M4 и M5 к новой службе. Новых команд не требуется.

### Начальное состояние

- Подготовленная преподавателем `jdu-final.service` имеет состояния `loaded`, `inactive`, `disabled`.
- `/srv/jdu-final` и `index.txt` отсутствуют.
- `jduwriter` и `jduviewer` не входят в `finalops`.

### Задание

1. Через `systemctl cat jdu-final.service` прочитайте `User`, `WorkingDirectory`, `ExecStart`.
2. Создайте `/srv/jdu-final` с владельцем и группой `root:finalops`, режимом `2775`.
3. Создайте `/srv/jdu-final/index.txt`. Его содержимым должна быть та же единственная строка, что в `/etc/jdu-lab/final-marker`.
4. Задайте для `index.txt` владельца и группу `root:finalops`, режим `664`.
5. Добавьте `jduwriter` в `finalops`, но не добавляйте `jduviewer`.
6. Проверьте, что writer может обновить содержимое, а viewer — нет.
7. Не меняя юнит, запустите службу и включите автозапуск.
8. Проверьте, что служба работает от имени `jdufinal` и слушает только `127.0.0.1:8090`.
9. Проверьте код HTTP `200` и указанный marker в ответе.
10. Отправьте запрос на `http://127.0.0.1:8090/m7-check`.
11. Найдите `REQUEST path=/m7-check` в журнале текущего запуска службы.

Для переключения из `ssm-user` используйте `sudo su - jduwriter` или `sudo su - jduviewer`. После каждой проверки возвращайтесь через `exit` к `ssm-user`. Перед `jdu-check M7` проверьте имя через `id -un`.

### Проверка

Оцениваются шесть пунктов: файлы, writer/viewer, служба, сокет, HTTP и журнал. Не меняйте файл юнита, настройки SSH и LabCheck.

```bash
jdu-check M7
```

Полезные команды: `id`, `getent`, `stat`, `chown`, `chmod`, `systemctl`, `ps`, `sudo ss -lntp`, `curl`, `sudo journalctl`.

## Запрещённые действия

- Не используйте `chmod 777`.
- Не меняйте `/etc/ssh/sshd_config`.
- Не останавливайте `ssh.service`.
- Не применяйте `killall` или `pkill` с широким шаблоном.
- Не выводите закрытый ключ, не сдавайте его и не добавляйте в Git.
- Не сканируйте внешние хосты и не пытайтесь войти в них.
